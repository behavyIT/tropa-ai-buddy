# security Specification

## Purpose
Аутентификация, защита API, ограничения частоты и проверка прав на каждом запросе.

## Requirements

### Requirement: Сессии
API SHALL требовать сессию (подписанный JWT в HttpOnly SameSite=Strict cookie или Bearer).

#### Scenario: [SEC-02] Вход и выход
- **WHEN** запрос без сессии, неверный пароль или неизвестный логин
- **THEN** 401; после входа `/api/me` возвращает роль и наставника, после выхода — 401

### Requirement: CSRF
Мутирующие запросы SHALL содержать заголовок `X-Requested-With: tropa`.

#### Scenario: [SEC-03] Запрос без заголовка
- **WHEN** POST без заголовка
- **THEN** 403

### Requirement: Ограничение частоты
Вход SHALL ограничиваться 10/мин на IP, чат — 30/мин на пользователя; при недоступности Redis — fail-open.

#### Scenario: [SEC-04] Перебор паролей
- **WHEN** 11 попыток входа подряд
- **THEN** 429

#### Scenario: [SEC-07] Лимиты в памяти
- **WHEN** работает одна реплика без Redis
- **THEN** лимиты и лидер-лок крона работают в памяти

#### Scenario: [SEC-08] Лимиты в Redis
- **WHEN** несколько реплик используют Redis
- **THEN** лимиты общие, лок крона берёт одна реплика; при падении Redis — fail-open с ошибкой в логе

### Requirement: Проверка прав
Каждый эндпоинт SHALL проверять права по ролевой модели; недоступное SHALL выглядеть как отсутствующее (404) или запрещённое (403).

#### Scenario: [SEC-05] Матрица прав
- **WHEN** стажёр смотрит чужой маршрут, чужой наставник — маршрут, стажёр — согласования/аналитику/флаги
- **THEN** 404/403; свой наставник и HR BP — 200
